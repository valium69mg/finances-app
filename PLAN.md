# finances-app — Project Plan

Personal finance web app for a Mexican RESICO freelancer. Built from scratch as a
successor to the `~/finances` Python CLI (`fin.py`).

**Language rule (DECIDED):** the product is in Spanish; the codebase is in English.
- Spanish: everything the user sees in the frontend (UI copy, labels, messages, emails) and catalog/data values (categories, types, states, instrument types, payment methods), e.g. `KindIncome Kind = "Ingreso"`.
- English: identifiers (variables, functions, types, packages, constants' names), code comments, tests, docs, commit messages, API field names and file names.

Status: **planning**. No code exists yet. Decisions marked **OPEN** must be answered by
the owner before the affected work starts. Nothing is defaulted silently.

## 1. Goals

- Single-user web app (v1), run locally.
- One module per former Claude skill, each with its own tab.
- Dashboard as the main screen.
- Later: deploy to AWS, infrastructure provisioned with Terraform. Not part of v1.
- Out of scope for v1: the owner's wife / multi-user, wishlist, allowance tracking.

## 3. Architecture

Hexagonal, one module per bounded context:

```
finances-app/
  backend/
    cmd/api/                 # entrypoint
    internal/
      <module>/
        domain/              # pure logic, no I/O
        app/                 # use cases
        adapters/
          http/              # handlers
          postgres/          # repositories
  frontend/
  migrations/
  deploy/                    # production stack: Dockerfiles, compose, nginx (phase 6)
  infra/                     # Terraform (later)
```

Rules:

- Domain code is pure functions plus entities. No database, no HTTP.
- Money is an exact decimal (the `BigDecimal` equivalent), never `float64`. **DECIDED:** `shopspring/decimal` in Go, `NUMERIC` in PostgreSQL, and decimal strings in the JSON API. Rounding rules per calculation (e.g. SAT rounding) are defined explicitly and tested.
- Every tax and split calculation has tests with hand-computed cases from real numbers.

## 4. Modules (one tab each)

| Tab | Purpose (from the former skill) |
|---|---|
| Dashboard (main) | Monthly summary: budget vs. actual per category, available money, emergency fund progress, tax and payment status. Replaces `/finanzas`. Read-only (`backend/internal/dashboard`), endpoint `GET /dashboard?month=YYYY-MM` (default: current month; 422 `settings_incomplete` when budgets or the emergency fund goal cannot be computed). Contents: per-Gasto-category `spent`, `budget` (resolved with the month overrides of `GET /settings/budgets`, null when none), `remaining`, `over_budget`; month `income`, `expenses`, `savings` (net of withdrawals) and `available` = income - expenses - savings (as `fin.py`); `emergency` (all-time accumulated vs goal, from the savings domain); `tax`. Tax card **DECIDED:** the estimated RESICO ISR of the month and its rate, reusing the Income service estimate (`tax` is null when the tax settings are incomplete), plus the filing status from the Tax Filing module: `filing_status` is the payment state of the filing of the displayed month (`ninguna` when it is not filed, `pendiente` when filed and unpaid, `pagada`), `previous_period` is the month before and `previous_period_pending` is true when that period has issued invoices and no filing, or has a filing whose payment is pending (the card then warns and links to Declaraciones presentadas). The filing query only runs when the card exists. The card is a separate component and `tax` a separate object. The dashboard is the frontend root page (`/`). Additions **DECIDED:** the payload also carries `cycle` (`today` in `TZ_NAME`, `day` of the displayed cycle, 0 before it starts and clamped to `days` once over, `days` its length; the page compares spent against the total budget of the categories by cross-multiplying, so "above the pace" means spent/budget is ahead of day/days), `upcoming_bills` (the bills module `List` of active bills with a pending occurrence due within 14 days, overdue ones included, with `days_until_due` and `overdue`; the logic stays in bills), `recent_movements` (the 8 latest movements of any kind, a read-only `ListByRange` with no kind filter, newest first) and `future_expenses`. Future expenses **DECIDED:** the card shows the active items of the Future Expenses module (see its row), with `id`, `name`, `due_date`, `target`, `saved` (the savings linked to the item), `remaining`, `suggested_monthly` and `cycles_left`, the totals of the active items and `free_balance` (Gastos futuros savings linked to no item). A yearly bill is no longer the source: it is not necessarily something the owner saves for in advance (a small yearly domain renewal next to a large yearly tax), and paying one never released its savings, so the first heuristic (yearly fixed-MXN bills, with the net all-time `Gastos futuros` savings spread by earliest due date) was removed together with its code. The card links to Configuración, where the items are managed. The page cards are separate components (`CycleProgress`, `UpcomingBills`, `FutureExpensesCard`, `RecentMovements`). Phone layout **DECIDED:** `BudgetTable` renders compact cards below `md` (category and percent, full-width usage bar, "Gastado X de Y" and Restante / Excedido in red when over) and stays a table from `md` up, so there is no horizontal scroll on a phone. |
| Income | Register income (Sezzle in USD, client B in MXN) with the split rule for extra income. Replaces `/ingreso`. Storage: the shared `movements` table, only `kind = 'Ingreso'` (`backend/internal/income`). Amount rule **DECIDED:** an income amount must be greater than zero (domain plus CHECK, migration 000007); expenses too, only Ahorro may be negative. Defaults as in `fin.py`: payment method Transferencia, currency MXN, date today, USD rate from `fx_rate_applied`; an empty category is inferred from the description (Ingreso categories only). Split rule **DECIDED:** preview-only, matching `fin.py`: for the category "Contrato extra" the response carries a non-persisted `split` (SAT reserve, emergency fund, investments with the per-instrument breakdown, aguinaldo and vacation) computed on `amount_mxn`; the user records the Ahorro rows themselves. Auto-creating Ahorro rows was **rejected**. Sueldo gets no split. Creating or updating an income also returns the month's income total and the RESICO ISR estimate (rate, estimated ISR, whether the rate went up and the previous rate; null when the tax settings are incomplete). Endpoints: `POST /income`, `GET /income?month=&limit=`, `PUT /income/{id}`, `DELETE /income/{id}`, `GET /income/infer-category?description=`. Create forms **DECIDED** (also Expenses, Savings for the saving form only, and Bills): the create form is collapsed behind a "+ Nuevo ..." toggle (`InlineFormPanel`: expands inline, no modal, `aria-expanded`/`aria-controls`, focus to the first field on open and back to the toggle on close). It collapses after a successful save and after cancelling an edit; starting to edit a row opens it by itself and keeps the green edit highlight (`useFocusOnEdit`) on the form. |
| Expenses | Register expenses with category inference. Replaces `/gasto`. Storage **DECIDED:** a single shared `movements` table (migration 000006) holds Ingreso, Gasto and Ahorro; Expenses only reads and writes `kind = 'Gasto'`, and Income and Savings reuse the same table and repo (`backend/internal/ledger`). Amount rule **DECIDED:** an expense amount must be greater than zero (enforced in the domain and by a CHECK); only Ahorro may be negative (withdrawals). USD movements store the rate used, and `amount_mxn` is `amount * rate` rounded to cents. Defaults as in `fin.py`: payment method Débito, currency MXN, date today, USD rate from `fx_rate_applied`. Creating or updating an expense returns budget feedback for its month (spent vs. budget, over-budget flag, null budget when the category has none). Feedback is best-effort **DECIDED:** the expense is already saved when the feedback is computed, so a failing lookup is logged as a warning and the feedback is omitted (null) instead of failing the call (callers such as bills and tax filing would leave a saved expense unlinked and a retry would duplicate it); income does the same with its month summary (`summary` null) and split. Amount guard **DECIDED:** `ledger.CheckAmount` runs before any comparison, rounding or arithmetic on a user decimal: exponent between -32 and 12 and magnitude below 1e12 (the NUMERIC(14,2) range); movements (income, expenses, savings, also the MXN result), invoice preparation, tax filing, bills and the settings validators use it, and out-of-range values are the module's 400 `invalid_*` error (no memory blow-up, no 500 from a NUMERIC overflow). Endpoints: `POST /expenses`, `GET /expenses?month=&limit=`, `PUT /expenses/{id}`, `DELETE /expenses/{id}`, `GET /expenses/infer-category?description=`. |
| Savings | All savings: emergency fund, aguinaldo and vacation, future expenses, investments and SAT reserve. Replaces `/ahorro` and `/portafolio` (the Portfolio tab is dropped). Instrument tracking **DECIDED:** each savings entry picks an instrument (e.g. GBM liquidity, CETES 28/91, VOO, VXUS), and instrument valuations can be recorded to show current value and gains. Valuations are entered manually; no external price API. Valuations **DECIDED:** append-only (no edit or delete; a mistake is fixed by adding a later valuation), with an optional note; the instrument must exist in Settings. An instrument with no valuation is valued at its contributions ("sin valuar", gain 0). Future expense link **DECIDED:** an Ahorro row may carry `future_expense_id` (migration 000016, see Future Expenses); ordinary savings leave it NULL and editing a saving keeps it. Transfers **DECIDED:** `POST /savings/transfers` atomically creates two Ahorro movements (negative on the source instrument, positive on the target) in one transaction; the category is optional and inferred from the reverse of `instrumento_por_categoria` (source first, then target; last category in config order wins when several share an instrument, as in `fin.py`), else the request must specify it. Storage: Ahorro rows in the shared `movements` table, valuations in `valuations` (migration 000008). Endpoints: `POST /savings`, `GET /savings?month=&limit=`, `PUT /savings/{id}`, `DELETE /savings/{id}`, `POST /savings/transfers`, `POST /savings/valuations`, `GET /savings/valuations`, `GET /savings/portfolio` (rows per instrument, totals, subtotals by type and by destination, emergency fund progress). The page lives on the existing `/ahorros` tab. Transfer legs **DECIDED:** both legs share a nullable `transfer_id` UUID (migration 000009, exposed in the saving JSON, NULL on older rows); a leg is locked: `PUT` on it returns 409 `transfer_leg_locked`, and `DELETE` on either leg removes both in one statement (the page shows a "Traspaso" badge, hides Editar and warns that both legs go). Valuation values are rounded to cents before storing (the 201 returns the rounded value); a value that rounds to 0, is >= 1e12 or has an absurd exponent is a 400 `invalid_valuation`. An update keeps the stored date, payment method, currency and rate when the body omits them, and the ledger update is guarded by kind so a module never overwrites another module's movement. |
| Invoices | Prepare invoices, track their status, store the issued CFDI files. Replaces `/factura`. The app does **NOT** stamp (timbrar): it prepares the SAT-portal checklist (issuer, receiver, voucher, concept, taxes, totals, fiscal period and declaration due date; `to_confirm` items are the ones to confirm with the accountant) and the user stamps in the SAT portal. Amount rules as `fin.py` (`backend/internal/invoices`): client `usa` takes a USD subtotal (default `salary_usd`) and exchange rate (default `fx_rate_applied`), IVA 0%; any other client takes the total received with IVA included; amounts are rounded to cents (IVA = total - subtotal). States **DECIDED:** `preparada` -> `emitida` -> `cancelada`; cancelada is terminal, an emitida invoice can be cancelled, a cancelada one cannot be issued, an emitida one cannot be re-issued. Issue flow **DECIDED:** the user uploads the CFDI XML; the backend parses it with `encoding/xml` (size limit 1 MiB, DOCTYPE rejected, depth bounded, only `Comprobante` Total/SubTotal/Moneda and the `tfd:TimbreFiscalDigital` UUID are read) and stores the UUID; total, subtotal or currency differences with the prepared invoice are returned as `warnings`, never errors; the PDF (max 10 MiB, `%PDF-` magic) is optional; without an XML the user may type the UUID (8-4-4-4-12 hex, stored upper case); a UUID already used by another invoice is a 409 `duplicate_uuid`; a manual UUID that differs from the XML's is 422 `uuid_mismatch`. The same client and collection date on a non-cancelled invoice returns a `possible_duplicate` warning on prepare. Storage **DECIDED:** files go through the `ObjectStore` port to a private S3-compatible bucket (MinIO adapter with minio-go, bucket ensured on first use, see the startup note below; env `S3_ENDPOINT` default `localhost:9100`, `S3_BUCKET`, `S3_REGION`, `S3_USE_SSL`, credentials default to `MINIO_ROOT_USER/PASSWORD`); keys are random and never exposed; Postgres keeps only metadata (`invoice_documents`: kind xml|pdf, key, name, content type canonical to the kind, size, sha256; one current file per kind, replacing swaps the row and deletes the old object). Objects are uploaded before the DB write and removed if it fails. Download **DECIDED:** streamed by the backend behind auth (`Content-Disposition: attachment`, `nosniff`, `no-store`, CSP sandbox), never presigned URLs, so MinIO is not reachable by clients and nothing outlives the session. Tables (migration 000010): `invoices` (client, collection date, period, currency, exchange rate, subtotal, subtotal_mxn, iva, withholdings, total, expected deposit, state, unique nullable uuid, optional `movement_id` to an Ingreso, `declaration_period`, set by the Tax Filing module when a filing includes the invoice) and `invoice_documents`. Endpoints: `POST /invoices` (201 invoice, documents, checklist, warnings), `GET /invoices?period=&state=`, `GET /invoices/{id}?periodicity=` (periodicity quincenal|mensual only shapes the global-invoice checklist and is not stored), `POST /invoices/{id}/issue` (multipart: `xml`, `pdf`, `uuid`; xml or uuid required), `POST /invoices/{id}/documents` (multipart: `kind`, `file`; issued invoices only), `GET /invoices/{id}/documents/{docId}`, `POST /invoices/{id}/cancel`. Cancel rule **DECIDED:** an invoice included in a registered tax filing (`declaration_period` set) cannot be cancelled, because the saved declaration would silently go out of sync: 409 `invoice_declared`; the check is part of the `UPDATE` itself (`declaration_period IS NULL`), so it cannot race with a filing being registered, and the UI disables Cancel with an explanation (delete the pending filing first, which clears the link). Issued after filing **DECIDED:** issuing an invoice in a period that already has a filing is allowed but returns a `period_already_filed` warning (also shown in the issue flow); the invoice is never linked to that filing and its income stays undeclared, so it is surfaced by `GET /tax-filing/unfiled-invoices` (see Tax Filing). No complementary declaration is built. Startup **DECIDED:** the object storage is optional at boot: the API starts even when MinIO is down or the S3 credentials are missing (a warning is logged), the bucket is ensured lazily on first use and retried with backoff (1s doubling up to 30s), and only the file routes (issue with files, attach, download) answer 503 `storage_unavailable` until it is available, recovering without a restart; missing credentials disable the storage the same way. The credentials fallback to `MINIO_ROOT_USER/PASSWORD` stays. Amount guard **DECIDED:** every user decimal (subtotal, amount, exchange rate) is range-checked before any arithmetic, see Expenses. |
| Tax Filing | Compute the monthly RESICO declaration and register the filing made in the SAT portal. Replaces `/declaracion` and, together with Filed Records, `/declarado`. **One backend package** (`backend/internal/taxfiling`, DECIDED) serves two UI tabs: Tax Filing (`/declaracion`) and Filed Records (`/declaraciones-presentadas`). The app never files with the SAT. Inputs **DECIDED:** only `emitida` invoices of the period count (unlike `fin.py`, which also counted `preparada` ones); prepared invoices of the period are listed as a `prepared_invoices` warning, cancelled ones are ignored. Computation reuses `settings.ResicoRateOrFirst` and `income.ToMXN`: income = sum of `subtotal_mxn`, rate = RESICO bracket of that income (first bracket when there is none), ISR causado = income x rate, ISR a pagar = max(0, causado - retenido), IVA a cargo = trasladado - retenido - acreditable (negative means saldo a favor, never clamped, and it does not reduce the ISR), total a pagar = ISR a pagar + max(0, IVA), export base = subtotal of client `usa`. Every figure is rounded to cents (half away from zero); the rate keeps its configured value. IVA acreditable is an optional user input (query/body `iva_acreditable`, the official SAT term) and is stored with the filing. Due date rule **DECIDED** (as `fin.py`): the 17th of the month after the period (December rolls to January), with no holiday calendar, so the SAT may move it to the next business day. The preview is pure and never persists. The SAT reserve withdrawal of `fin.py registrar` was **dropped**: the payment expense is now opt-in and the reserve is managed from Savings. Endpoints: `GET /tax-filing/preview?period=YYYY-MM&iva_acreditable=` (period defaults to the previous month; returns the figures, the included invoices, `warnings` and the existing `filing` when the period is already filed), `POST /tax-filing` (register: period, `filing_date` default today, `folio`, `iva_acreditable`, optional `payment {date, isr_paid, iva_paid, record_expense}`; 201 `{filing, warnings}`), `GET /tax-filing?year=&status=`, `GET /tax-filing/pending-periods`, `GET /tax-filing/{period}` (filing plus its invoices), `POST /tax-filing/{period}/payment`, `DELETE /tax-filing/{period}`, `GET /tax-filing/unfiled-invoices`. Unfiled invoices **DECIDED:** issued invoices that no filing includes although their period is already filed (issued after the filing, `declaration_period` empty) are listed by `GET /tax-filing/unfiled-invoices` (a separate list, not a flag on the pending periods) and shown as an alert in Filed Records; the app only surfaces them, it does not build a complementary declaration. Amount guard **DECIDED:** `iva_acreditable` and the paid amounts are range-checked before any comparison or rounding (see Expenses); out of range is 400 `invalid_filing`. `MonthStatus` (dashboard) reads only the filings of the month and of the previous period and, when that one is not filed, its issued invoices, never every invoice and filing. Errors: 400 `invalid_filing` / `invalid_expense`, 404 `not_found`, 409 `already_filed` / `already_paid` / `filing_paid` / `invoices_changed`, 422 `settings_incomplete`. Storage **DECIDED** (migration 000011): `tax_filings` keyed by `period` (one filing per period), NUMERIC(14,2) amounts, `isr_rate` numeric, `folio`, `payment_date`/`isr_paid`/`iva_paid` (all set or all NULL) and `expense_movement_id` (FK to `movements`, `ON DELETE SET NULL`); the included invoices are the ones whose `declaration_period` equals the period (no array column), linked in the same transaction as the insert, which fails with `invoices_changed` when the issued invoices differ from the ones the declaration was computed from. Payment **DECIDED:** a filing is registered pending (no payment) or paid (a `payment` in the same request) and a pending one is paid later with the amounts and date the user actually paid (they default to the amounts due in the UI, 0 for an IVA balance in favor); a filing is `pendiente` until its payment exists, then `pagada` (API status values are Spanish catalog data). Recording the payment as an expense is opt-in (`record_expense`, unchecked by default, never silent): it creates an Impuestos expense in MXN dated on the payment date for ISR + IVA paid through the expenses service (so its rules stay in one place), links its id to the filing, and needs a total above zero; if the filing write fails after the expense was created, the expense is removed again. Corrections **DECIDED:** a filing is append-only once paid (no edit, no delete, `filing_paid`), like valuations; a **pending** filing may be deleted (it moves no money and has no expense), which clears `declaration_period` on its invoices and frees the period so it can be registered again. Figures cannot be typed: they always come from the computation. |
| Filed Records | History of filed declarations and payments (`GET /tax-filing`, filters year and status) plus the periods still to file (`GET /tax-filing/pending-periods`: months with `emitida` invoices and no filing, each with its due date and an overdue flag, as `fin.py` lists "Periodos pendientes de declarar"). Replaces `/declarado`. Same backend package as Tax Filing. The page (`/declaraciones-presentadas`) has the pending periods with a shortcut to declare each one, a table with status badges (Pago pendiente / Pagada), a detail panel (figures, invoices, payment, linked expense, delete a pending record) and a dialog to record the payment with the optional "Registrar el pago como gasto (Impuestos)" checkbox. |
| Month Close | Monthly snapshot: over-budget categories, suggestion for where to put the leftover money (emergency fund first, then investments), budget-adjustment hints for deviations over 20%. Stored in the database. Replaces `/cierre-mes`. **Built** (`backend/internal/monthclose`, tab Cierre de mes at `/cierre-de-mes`). Snapshot **DECIDED:** a stored close is immutable, the figures as of the moment it was generated, so editing movements later never changes it (`fin.py` wrote a markdown file for the same purpose). Contents: per-Gasto-category `spent`, `budget` (resolved with `settings.MonthBudgets`, so per-month overrides and the pause apply), `remaining`, `over_budget` (the dashboard definition and rows are reused, never duplicated); month `income`, `expenses`, `savings` (net) and `available` (the dashboard totals); `emergency` (accumulated **as of the end of the closed period**, not today, against the goal); `suggestion`; `adjustments`; `tax_filing_status` (the Tax Filing payment state of the period at closing time, from the same `MonthStatus` the dashboard uses). Suggestion rule **DECIDED** (as `fin.py`, plus the pause): only when `available` is positive; the emergency fund first, up to its remaining room to the goal; the remainder goes to Inversiones, or to Gastos futuros when the period is one of the paused months (`inversiones_pausa`), so Inversiones is never suggested while paused and a complete fund sends everything to Inversiones (or Gastos futuros while paused). Hint rule **DECIDED** (as `fin.py`): Gasto and Ahorro categories with a non-zero budget whose real amount deviates from it by more than 20% (over or under, compared without dividing, so exactly 20% is not a hint; the signed percentage is reported); categories without a budget or with a zero budget are ignored. The hints never change the settings. Endpoints: `GET /month-close/preview?period=YYYY-MM` (default: the previous month; pure, never persists; returns `{preview, existing}` where `existing` is the stored close of the period or null), `POST /month-close` (`{period}`; stores the snapshot, 201; a future period is 400 `invalid_close`, the current month is allowed as a mid-month snapshot; 409 `already_closed` when one exists), `GET /month-close` (history, newest period first), `GET /month-close/{period}` (404 `not_found`), `DELETE /month-close/{period}` (204). Errors: 400 `invalid_close`, 404 `not_found`, 409 `already_closed`, 422 `settings_incomplete` (budgets or the emergency goal cannot be computed). Delete rule **DECIDED:** a close can be deleted so it can be regenerated after correcting movements; deleting removes only the snapshot and never touches movements. Table (migration 000013): `month_closes` keyed by `period` (one close per period), `closed_at`, unscaled NUMERIC columns `income`, `expenses`, `savings`, `available`, `emergency_accumulated`, `emergency_goal` (exact as computed), `tax_filing_status`, and JSONB documents `categories`, `suggestion` (nullable) and `adjustments` whose money values are decimal strings. The page has the month selector (default the previous month), the preview with the close action behind a confirmation dialog (disabled for a future month and hidden when the period is already closed), the history of stored closes with a detail view and the delete action behind a confirmation that warns the snapshot is discarded. |
| Bills & Subscriptions | Recurring bills and subscriptions (e.g. monthly water bill) with periodic reminders. A bill occurrence can be marked paid, which registers an expense. Later: a scheduled job that emails about bills that are about to expire or were never registered. Recurrence **DECIDED:** weekly, biweekly, monthly, bimonthly, yearly (no custom intervals). Amount **DECIDED:** a bill has either a fixed amount or no amount. Amount guard **DECIDED:** the bill amount and the payment amount are range-checked before any rounding (see Expenses): above 999,999,999,999.99 or a huge exponent is 400 `invalid_bill`, never a 500. When marking it paid, the expense amount defaults to the bill's amount when it has one, and can always be overridden (discounts, price changes). Overdue occurrences **DECIDED:** stay pending and flagged overdue until paid or manually skipped (skip registers no expense; no auto-skip). Reminder lead time **DECIDED:** configurable per bill. Category **DECIDED:** each bill has a default expense category, changeable when marking it paid. Occurrences **DECIDED:** only the next occurrence exists at a time; paying or skipping it generates the following one. **Built** (`backend/internal/bills`, tab Pagos recurrentes at `/pagos-recurrentes`). Tables (migration 000012): `bills` (name, default expense category, optional fixed `amount` + `currency` MXN/USD, `recurrence`, `next_due_date`, `anchor_day`, `reminder_lead_days` default 3, `active`, `notes`) and `bill_occurrences` (`bill_id`, `due_date`, `status` pending/paid/skipped, `paid_on`, `expense_movement_id` nullable with ON DELETE SET NULL, `amount_paid`, `currency`, `resolved_at`); a partial unique index allows one pending occurrence per bill, and paid/skipped rows are the history. Next due date: month steps land on `anchor_day` (the day of the date the user set) clamped to the last day of shorter months, so a bill due on the 31st goes Jan 31, Feb 28, Mar 31 without drifting; yearly Feb 29 falls on Feb 28 in common years; editing the due date re-anchors, resending the current one keeps the anchor. Endpoints: `POST /bills`, `GET /bills?include_inactive=` (active bills with the pending occurrence, computed `overdue` (due date before today) and `due_soon` (within `reminder_lead_days`, due today included), `days_until_due`, sorted by due date), `GET /bills/{id}` (with the resolved history), `PUT /bills/{id}`, `DELETE /bills/{id}`, `POST /bills/{id}/pay` (`{date?, amount?, category?, description?}`; `amount` required when the bill has none), `POST /bills/{id}/skip`. **DECIDED:** `DELETE` deactivates (`active = false`), never removes: history and the expenses of past payments stay, an inactive bill cannot be paid or skipped (409 `bill_inactive`), and `PUT` with `active: true` reactivates it. Paying creates the expense through the expenses service (defaults, USD rate and category validation stay there; the description defaults to the bill's name), then marks the occurrence paid and generates the next one in one transaction; if that fails the expense is deleted again, and a double payment gets 409 `occurrence_resolved`. Email reminders and the scheduler are not built: phase 7 will read `reminder_lead_days`, `due_soon` and `overdue`. Import **DECIDED:** see the data import note. |
| Future Expenses | Explicit things the owner chooses to save for ("Gastos futuros"), managed in the **Configuración** tab, section "Gastos futuros" (**DECIDED:** one place for registering, editing, deleting and the day-to-day actions: add saving, assign from the free balance, Marcar pagado). **Built** (`backend/internal/futureexpenses`, endpoints under `/future-expenses`). Why not bills **DECIDED:** a yearly bill is not necessarily saved for in advance and paying one never released savings, so a dedicated model replaced the bill heuristic. Table (migration 000016): `future_expenses` (`name` up to 120 chars, `target_amount` numeric(14,2) > 0, MXN only for now, `due_date`, `status` `active` | `paid`, `paid_at` date, `amount_paid`, `expense_movement_id`, `created_at`, `updated_at`; a CHECK ties the paid columns to the status; there is no owner column, like every other table today). ## 5. Auth (v1)

- Login page. Single admin user, email `carlostranquilino.cr@gmail.com`.
- Seeding **DECIDED:** the admin is seeded into PostgreSQL with only that email and a random password (stored as a bcrypt hash). No password or hash comes from `.env`, and no plaintext credential is ever in source or git history. The seed marks the user **unverified** (flag on the user row). A `.env.example` with placeholders is committed; the real `.env` is not.
- Email verification **DECIDED:** while the unverified flag is on, logging in leads to a forced flow: the app sends the user an email through Resend to verify the address and change the password. Completing it clears the flag. Resend API key comes from `RESEND_API_KEY` (in `.env`, placeholder in `.env.example`).
- First credential **DECIDED:** the admin never needs the random password. Verification is triggered from the identify step (below), not from the login form.
- Email-first login **DECIDED (supersedes the earlier single-form flow):** two steps.
  1. `POST /auth/identify {email}` returns `200 {"status":"password_required"}` when the account exists and is verified, and `200 {"status":"verification_sent"}` when it is unverified OR unknown. Unverified accounts get the verification email in the background; unknown emails send nothing but look identical to unverified. Invalid email format: `400 invalid_email`. Rate limited: `429 rate_limited`.
  2. Verified users enter the password: `POST /auth/login {email,password}` only authenticates. Unknown, unverified and wrong-password all return `401 invalid_credentials`; login never sends email and no longer has a 202 path.
- Account enumeration **DECIDED (accepted by the owner):** identify discloses that an email is a verified account. Nothing else leaks (unknown and unverified are indistinguishable). This is accepted in exchange for a login page that no longer asks for a password that would be ignored.
- Rate limits **DECIDED** (app layer, in-memory fixed windows, per process; client IP is the socket peer, and the `X-Real-IP` header is believed only when the peer is inside the configured `TRUSTED_PROXIES` list, empty by default, see phase 6; `X-Forwarded-For` and the other forwarding headers are never read):

  | Limit | Scope | Budget | Counts |
  | --- | --- | --- | --- |
  | identify | per IP | 10 per 15 min | every identify call; deliberately NO per-email limit (it would let anyone lock the owner out) |
  | verification email | per email | 1 per 60 s and 5 per hour | emails actually sent; when exceeded the email is silently not sent, the response stays `verification_sent` and it is logged at Info; suppressed requests do not consume the other budget |
  | login | per email 5, per IP 20 | per 15 min | FAILED attempts only (wrong password, unknown or unverified email); successes and identify calls never consume it; the budget is checked before the password is verified and `429` is returned when exhausted |
  | refresh | per IP 60 | per 15 min | every `POST /auth/refresh` (success or not), checked before the token is looked up, so a limited call never consumes or rotates a token; `429 rate_limited` with `Retry-After`. A session rotates about once per 15 min per tab, so normal use (many tabs, reloads, a shared NAT) stays far below the budget; it only stops floods against the token table |
  | verify | per IP 10 | per 15 min | every `POST /auth/verify` (success or not), checked before the password is hashed (each attempt costs a bcrypt hash); a weak password is rejected without burning the token, and a real user needs one or two attempts; `429 rate_limited` with `Retry-After` |

  Accepted trade-off: 5 failed logins lock that email for 15 minutes from every IP, so an attacker can delay the owner's password step (not step one, and not verification emails). Revisit with per-IP-and-email keys or a CAPTCHA if it becomes a problem.
- Verification token **DECIDED:** 32 random bytes (base64url), stored SHA-256 hashed, 1 hour lifetime, single use.
- Resend sender **DECIDED:** `onboarding@resend.dev` for now, overridable via `RESEND_FROM`; a custom domain comes later.
- Unverified users **DECIDED:** never receive a session, so there is nothing an unverified session can access.
- Session mechanism **DECIDED:** JWT access token (15 min) plus an opaque refresh token, both returned in the login response body. No cookies.
- Refresh flow **DECIDED:** using a refresh token issues a new JWT and a new refresh token, and invalidates the used one (rotation). Refresh tokens are stored hashed in PostgreSQL.
- Refresh token lifetime **DECIDED:** 7 days.
- JWT signing **DECIDED:** HS256. The secret comes from configuration, never from source.
- Client-side token storage **DECIDED:** localStorage for both tokens. Accepted risk: an XSS bug could read them, so the frontend must avoid `dangerouslySetInnerHTML`, ship a strict Content-Security-Policy, and keep dependencies minimal.
- Refresh token reuse **DECIDED:** presenting an already-used refresh token revokes all of the user's refresh tokens.
- Logout **DECIDED:** `POST /auth/logout` revokes the presented refresh token; the client clears localStorage.

## 10. Visual design decisions

- **Kind colors** (tokens in `frontend/src/index.css`, registered in `tailwind.config.js`, light and both dark blocks): Ingreso emerald (`income`), Gasto violet (`expense`), Ahorro sky (`saving`). Kinds: Ingreso ArrowDownLeft, Gasto ArrowUpRight, Ahorro PiggyBank. Section icons live next to each card heading (`CardTitle`, `IconChip`, `PageTitle`); empty states use `EmptyNote`.
- **Category icons:** `src/lib/categoryIcon.ts` maps a category name to an icon by accent-insensitive keyword prefix (first match wins), with Sparkles as the fallback.
